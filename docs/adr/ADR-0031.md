# ADR-0031: Literal defaults and expression defaults are written differently

- Status: Accepted
- Date: 2026-10-26
- Deciders: Rommel

## Context

The spec's example `default: newGuid()` cannot be told apart from a string literal: `default: Open` could be the text "Open" or an identifier. `newGuid()` was also not among the built-in functions.

## Decision

- `default:` is always a literal of the field's type (string, number or boolean). Lint checks the literal fits the type (RADD211).
- A computed default is written `default: { expression: "newGuid()" }`.
- `newGuid()` joins the RADD built-in functions, and `ctx.now` joins the server-supplied values next to `ctx.today` and `ctx.locale`.
- In canonical JSON a default is `{ value: <literal> }` or `{ expression: "<CEL>" }`.

## Alternatives considered

- **Guess from the text (a string ending in `()` is an expression).** Fragile and surprising.
- **A prefix such as `=newGuid()`.** Compact, but easy to miss in review and awkward for schemas.

## Consequences

- Spec examples use the object form.
- Which expression defaults can become database defaults (for example `ctx.now` as `CURRENT_TIMESTAMP`) is decided in stage 3.
