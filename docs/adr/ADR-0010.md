# ADR-0010: Structured logging with consistent property names and a defined use of levels

- Status: Accepted
- Date: 2026-10-26
- Deciders: Rommel

## Context

Validation failures, warnings and dictionary problems must be diagnosable in production across the API and the browser, without leaking personal or financial data, and with whatever logging stack a team already uses.

## Decision

- The API logs through `Microsoft.Extensions.Logging` with source-generated `LoggerMessage` methods, stable event IDs and named properties (`{Entity}`, `{Path}`, `{Code}`, `{Severity}`, `{DictionaryVersion}`). A logging scope carries the trace ID, entity and dictionary version.
- Values of fields tagged `pii` or `financial` are never logged; entries carry the path and code only.
- The TypeScript client logs every validation error and warning through a logger interface supplied at setup (no-op by default), with the same property names.
- Levels: Trace for per-rule evaluation detail; Debug for metadata served, lookup cache hits and EF configuration detail; Information for dictionary loaded, 422 rejections and acknowledged warnings saved; Warning for interceptor failures after passing the API boundary, translation fallbacks and stale client versions; Error for a throwing validator or lookup query and runtime expression failures; Critical for an invalid dictionary or a declared validator with no implementation at startup.

## Alternatives considered

- **Formatted string messages.** Hard to query and correlate.
- **A RADD-specific logging library.** Teams already have one; RADD plugs into theirs.

## Consequences

- Client and API logs can be correlated and queried together.
- Tags on fields affect logging, so `pii` and `financial` must be applied with care.
