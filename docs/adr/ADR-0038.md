# ADR-0038: Hand-written JSON is JSONC; JSON Schemas are generated from JSONC sources

- Status: Accepted
- Date: 2026-10-27
- Deciders: Rommel

## Context

The repository has hand-written JSON: the JSON Schemas, tool configuration (Biome, TypeScript, VS Code, the .NET SDK) and conformance vector files. Strict JSON has no comments, so the reasons behind non-obvious choices (a per-kind `if`/`then` instead of `oneOf`, a Biome exclusion, a vector's purpose) lived only in commit messages and ADRs, away from the line they explain. The published JSON Schemas, though, are fetched by URL by editors and validators that expect strict JSON.

## Decision

- Every hand-written JSON file is JSONC. Where the tool accepts comments in a `.json` file (`tsconfig*.json`, `.vscode/*.json`, `dotnet/global.json`) the name stays; otherwise the file is named `.jsonc` (`biome.jsonc`, `vector.jsonc`).
- JSON Schemas are written in `schema/src/*.schema.jsonc`. `npm run schema:build` (`scripts/build-schemas.mjs`) writes strict `schema/v1/*.schema.json`: comments dropped, `$id` unchanged (and checked to match the output file), a `$comment` naming the source added after `$id`, two-space indentation, LF and a trailing newline. It also removes outputs with no source.
- The generated `schema/v1` files are committed, because they are the published form (`$id` URLs on GitHub) and what editors and `radd lint` load. `npm run schema:check` fails if they are out of date; CI runs it, and a test does the same check in `npm test`. Never edit `schema/v1` by hand.
- Conformance: hand-written vector files (manifests now, input records later) are JSONC. Dictionaries in vectors stay YAML; expected results stay strict JSON.
- Strict JSON remains only where a tool or contract requires it: `package.json` and lockfiles, generated output (the canonical dictionary, conformance expected results, `schema/v1`, build artifacts) and API payloads.
- JSONC is parsed with `jsonc-parser` without trailing commas, so a file stays valid for every JSONC reader.

## Alternatives considered

- **Keep strict JSON, explain things in `description` or `$comment`.** `description` is shown to dictionary authors as hover text, so maintainer notes would clutter it; `$comment` works only in schemas and is awkward for multi-line notes.
- **Publish the JSONC schemas directly.** Many validators and editors fetch a schema by URL and parse it as strict JSON, so comments would break them.
- **Author schemas in YAML or JSON5.** Both allow comments, but add a second syntax for the same content and are less familiar to schema tooling; JSONC is JSON plus comments, and VS Code already understands it.
- **Generate `schema/v1` at publish time only, uncommitted.** The `$id`s point at `schema/v1` on `main`, and the editor settings and tests read it from the repository, so the output must be in the repository.

## Consequences

- Schema changes are two files in a pull request: the source and its generated output. Reviewers read the source; `.gitattributes` marks `schema/v1` as generated so GitHub collapses it.
- Forgetting `npm run schema:build` fails CI and `npm test` with a message saying what to run.
- Biome formats the JSONC sources and skips `schema/v1`. It needs an override to accept comments in `dotnet/global.json`.
- `jsonc-parser` is a development dependency. `@radd/core` reads only the strict `schema/v1` files, so it needs no JSONC parser at run time.
