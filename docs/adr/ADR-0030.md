# ADR-0030: Message keys are derived from the path and resolved at build time

- Status: Accepted
- Date: 2026-10-26
- Deciders: Rommel

## Context

Every label, hint and message is a key into `i18n/`. Writing every key by hand is noisy; resolving the field-to-domain-to-framework fallback at run time in every runtime duplicates logic and risks differences.

## Decision

- Entities, domain types and lookups share one message-key namespace, prefixed by the lowerCamel name (`OrderLine` becomes `orderLine`). Lint rejects two definitions with the same prefix and the reserved prefix `radd` (RADD103).
- Text keys: an entity has `<entity>.displayLabel` (required) and optional `<entity>.pluralLabel` and `<entity>.displayHint`. A field has `<entity>.<field>.displayLabel` (required) and optional `shortLabel`, `displayHint` and `placeholder` under the same prefix. A field may name its own key for any of the four; an explicitly named key must exist.
- Optional keys appear in the canonical JSON only when the default locale has them.
- Constraint messages (`required`, `type`, `maxLength`, `minLength`, `min`, `max`, `precision`, `scale`, `format`, `pattern`, `lookup`) are resolved at build time to the first key that exists in the default locale, in this order: `<entity>.<field>.<constraint>`, `<domainType>.<constraint>`, then the framework key (`radd.required`, `radd.format.email`, ...). The canonical field carries the result as `messages: { <constraint>: <key> }`.
- Rule and validator codes: a rule's `code` defaults to its `message` key. A validator use's message defaults to `<entity>.<field>.<validatorName>`, then the validator's declared `message`, and its code to `<entity>.<field>.<validatorName>`. Expression rules must name a message.
- `@radd/core` ships the framework's `radd.*` messages in English. A dictionary's i18n overrides them; other locales supply their own or fall back with one warning per locale (RADD502).
- Messages are ICU MessageFormat; `{label}` is the field's display label. Lint parses them with HTML tags treated as text.

## Alternatives considered

- **Resolve the fallback chain at run time.** Every runtime would implement it, and the hash would not reflect which text is used.
- **Write every key explicitly in the entity files.** Verbose and error-prone; derivation keeps entity files short.

## Consequences

- Adding a field-specific message changes the resolved key and therefore the hash.
- Unused keys are reported (RADD503), so i18n files stay in step with the dictionary.
