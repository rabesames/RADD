# ADR-0035: Foreign keys, relationships and lookup defaults

- Status: Accepted
- Date: 2026-10-26
- Deciders: Rommel

## Context

The spec says a reference-table lookup creates a foreign key, and lists relationships as an entity property, but not every foreign key is a lookup a user picks from (OrderLine.orderId), and navigations need names for generated code.

## Decision

- A plain foreign key is declared on the field: `references: { entity, field, onDelete }`. `field` defaults to the target's single-field primary key; `onDelete` is `restrict` (default), `cascade` or `setNull`.
- A reference-table lookup (`lookup: { entity, value, display }`) implies `references: { entity, field: value, onDelete: restrict }` unless the field declares its own.
- Navigations are declared on the entity under `relationships`, by name: `manyToOne` (this entity holds `foreignKey`), `oneToMany` (the related entity holds `foreignKey`) and `manyToMany` (`through` a join entity).
- A reference-table lookup's `cache` defaults to `ttl`, since reference data changes at run time and `static` would serve stale values; its `ttl` defaults to `lookups.defaultTtl` in `dictionary.yaml`, itself defaulting to `10m`.
- Lint checks every entity and field these name (RADD203, RADD204) and that a foreign key's type matches the referenced field's type (RADD210).

## Alternatives considered

- **Infer relationships from foreign keys.** Navigation names would have to be guessed.
- **Default `cache: static`.** Matches the spec example's Country lookup, but is wrong for most reference tables.

## Consequences

- Stage 3 maps `references` to EF foreign keys and `relationships` to navigation properties.
