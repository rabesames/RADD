# ADR-0003: Generate entity classes and interpret the dictionary at run time for everything else

- Status: Accepted
- Date: 2026-10-26
- Deciders: Rommel

## Context

The backend needs strongly typed entities for EF Core, LINQ and application code, but generating every layer (validators, EF configuration, endpoints) as code would create large generated surfaces that drift, are hard to review, and must be regenerated for every rule change.

## Decision

- In .NET, a Roslyn incremental source generator emits `partial` POCOs (properties and navigation properties only, no attributes) and a strongly typed key catalog (`Radd.Customer.Email`). Generated code is never edited or checked in; developers add behavior in their own partial files. `radd gen csharp` produces the same output for teams that prefer checked-in code.
- Everything else (EF model configuration through `ApplyDataDictionary()`, validation, `/_radd/*` endpoints, localization) interprets the canonical dictionary at run time, using each framework's native features.

## Alternatives considered

- **Generate everything.** Maximum compile-time checking, but large generated code that hides the dictionary's intent and must be regenerated and reviewed on every change.
- **Interpret everything, including entities.** No generated code, but no compile-time types for application code and LINQ.
- **Hand-written entities checked against the dictionary.** Duplicates every field definition, which is the problem RADD exists to solve.

## Consequences

- Application code gets compile-time safety where it matters (entity properties, key names).
- Rule changes take effect on rebuild without regenerating anything beyond entities.
- Each runtime needs a dictionary interpreter; the conformance suite (ADR-0023) keeps them consistent.
- How the generator gets the dictionary (MSBuild step running `radd build`, or parsing YAML in C#) is decided in stage 2, spike D.
