# ADR-0027: JSON Schema draft 2020-12, validated with Ajv, with a keyword set editors understand

- Status: Accepted
- Date: 2026-10-26
- Deciders: Rommel

## Context

The same schema must drive editor autocomplete and inline errors (the VS Code YAML extension), `radd lint`, and AI agents. Error messages must point at the right line and read clearly.

## Decision

- One JSON Schema (draft 2020-12) per file type in `schema/v1/`, with shared definitions in `common.schema.json`, and a `description` on every property for editor help text.
- `$id`s are `https://raw.githubusercontent.com/rabesames/RADD/main/schema/v1/<file>.schema.json` until the project has its own domain; changing them is its own ADR.
- The schemas avoid keywords the VS Code YAML extension does not support (`unevaluatedProperties`, `$dynamicRef`); objects use `additionalProperties: false`, so shared constraint properties are listed in each schema by `$ref`.
- The schemas check structure only. Cross-file references, naming, descriptions and translations are checked by lint with their own codes.
- `radd lint` validates with Ajv (strict mode, `allowUnionTypes`), and folds Ajv's per-branch errors for `anyOf`, `oneOf` and `if`/`then` into one message per problem (RADD102), with "did you mean" hints for unknown properties and enum values.

## Alternatives considered

- **Draft-07.** Widest editor support, but 2020-12 is current and Ajv supports both; the keyword restriction covers the editor gap.
- **@hyperjump/json-schema.** Fully compliant, but less detailed error output for mapping back to YAML.
- **Naming conventions and required descriptions in the schema.** Would give inline editor errors, but without distinct codes or the option to make them warnings.

## Consequences

- Editor validation and lint agree on structure; lint reports more.
- Adding a property means updating the schema and, where shared, every schema that lists it.
