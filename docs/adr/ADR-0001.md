# ADR-0001: Record decisions as immutable architecture decision records

- Status: Accepted
- Date: 2026-10-26
- Deciders: Rommel

## Context

RADD is built in stages with an AI agent (Claude) writing most of the code and Rommel deciding at each stage gate. Decisions made in conversation or in a spec paragraph are easy to lose, reinterpret or quietly change, and an agent working in a later session has no memory of why something was chosen. Companies adopting RADD also need to see why the framework works the way it does.

## Decision

- Every architectural or Rommel-level decision is recorded as an ADR in `docs/adr/ADR-NNNN.md` (four-digit sequence, never reused, including for rejected ADRs), committed in the same pull request as the code it governs, using the template in `docs/adr/template.md`.
- An ADR is needed for every decision recorded in the requirements spec, any choice between alternatives with lasting consequences (a library, file format, public contract, layering rule, naming convention, security or licensing stance), and any decision Rommel makes at a stage gate. Implementation details that can change freely within one package do not need one.
- Statuses: Proposed, Accepted, Hardened, Rejected, Superseded, Obsolete. Only Rommel sets Hardened; Claude never does.
- A Hardened ADR is immutable except that its status may become Superseded or Obsolete, with a Superseded-by line. Superseded, Obsolete and Rejected ADRs never change. A changed decision gets a new ADR that names the old one under Supersedes.
- `docs/adr/README.md` is the index (number, title, status, date, links) and is updated in the same pull request as any ADR or status change.
- A CI check (`scripts/check-adrs.mjs`) enforces the immutability rules against the base branch and keeps the index in sync with the files.

## Alternatives considered

- **Decisions only in the spec.** The spec states the current design but not what was rejected or why, and edits overwrite history.
- **Mutable ADRs.** Simpler, but a hardened decision could drift silently, which defeats the point of a gate.
- **A wiki or issue tracker.** Lives outside the repo, so it is not versioned with the code and agents cannot rely on it being present.

## Consequences

- Every stage pull request carries its ADRs, and reviewing them is part of the gate.
- The history of a decision is a chain of ADRs linked by Supersedes and Superseded by.
- CI blocks accidental edits to hardened decisions, including by agents.
