# ADR-0032: Lint diagnostics, rule codes and the CLI contract

- Status: Accepted
- Date: 2026-10-26
- Deciders: Rommel

## Context

People, CI and AI agents act on lint results. Codes must be stable so that docs, suppressions and agents can refer to them, and locations must be exact.

## Decision

- Every diagnostic has `code`, `rule`, `severity` (`error`, `warning`, `info`), `message`, `file` (relative to the dictionary folder in the library; relative to the working directory in CLI output), `line`, `column`, `path` (JSON pointer) and an optional `hint` ("did you mean", or how to fix it).
- Codes are `RADD` plus three digits, grouped: 1xx files and schema, 2xx references and types, 3xx naming, 4xx documentation, 5xx localization, 6xx renames, 7xx expressions, computed fields and patterns. Codes are never reused. `docs/lint-rules.md` is the reference.
- Semantic rules run only on files that pass YAML and schema checks, so one mistake does not cascade; unused-key warnings are suppressed while any file fails.
- `radd lint [dir]` and `radd build [dir] [--out file]` default `dir` to `./dictionary`. Text output is one line per diagnostic (`file:line:column  severity  CODE  message`, hint below) and a summary. `--json` prints `{ ok, errorCount, warningCount, diagnostics }`, plus `version` and `out` for build, or `{ ok: false, error }` for usage errors.
- Exit codes: 0 success (warnings allowed), 1 lint errors, 2 usage or internal errors.

## Alternatives considered

- **Descriptive slugs only (`unknown-lookup`).** Readable but easy to rename by accident; RADD keeps both a code and a rule name.
- **Running semantic rules on schema-invalid files.** More findings per run, but rules would have to guard against every malformed shape and would report follow-on errors.

## Consequences

- A file with a schema error shows its semantic errors only after the schema error is fixed.
- New rules take new codes; retired codes stay reserved.
