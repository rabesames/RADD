# ADR-0004: A headless TypeScript client with TTL-cached metadata from the API

- Status: Accepted
- Date: 2026-10-26
- Deciders: Rommel

## Context

The front end must show field metadata, drive form state and validate for user experience using the same rules the API enforces, without re-typing them. Teams use different UI libraries, and a component library is out of scope for v1.

## Decision

- `@radd/client` is framework-agnostic and has no UI. It fetches client-safe metadata from `GET /_radd/metadata` at startup, caches it in memory and IndexedDB with a configurable TTL, and revalidates with the ETag.
- If any API response carries a `RADD-Version` different from the cached one, the client refreshes immediately.
- It exposes field metadata, conditional form state (`evaluate`), client-side validation in the API's result shape (`validate`) and lookups that honor the cache modes.
- The API remains authoritative; the client validates for user experience only.

## Alternatives considered

- **Bundle the dictionary into the front-end build.** Simpler loading, but the front end and API can disagree after a deployment, and server-only details risk being shipped.
- **A component library first.** Couples RADD to one UI framework; deferred to a separate project.
- **No client; call `/_radd/validate` for everything.** Correct but slow and chatty for interactive forms.

## Consequences

- One cached download per dictionary version; deployments mid-session are handled by the version header.
- Server-only rules and details never reach the browser.
- Form-library adapters (React Hook Form, TanStack Form) can be added without changing the core.
