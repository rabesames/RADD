# ADR-0006: Computed fields from the database or the application, declared explicitly

- Status: Accepted
- Date: 2026-10-26
- Deciders: Rommel

## Context

Some values are derived: a line total, a normalized search name, an order total that needs other rows. Teams compute them in SQL, in application code, or both, and the UI needs to know which fields are derived so it can show them read-only.

## Decision

A computed field declares its source in a `computed` block and is always read-only:

| Source | Declared as | Behavior |
| --- | --- | --- |
| database | `{ source: database, sql: { sqlite: ..., sqlserver: ..., postgres: ... }, stored }` | Computed column (EF `HasComputedColumnSql`); the CLI fails if an enabled database has no SQL |
| application, persisted | `{ source: application, expression: ..., persisted: true }` | CEL evaluated by the runtime before validation on every save, then stored |
| application, not persisted | `{ source: application, expression: ..., persisted: false }` | Evaluated on read; no column |
| application, server code | `{ source: application, calculator: name }` | A named calculator declared in `calculators.yaml` and registered in DI |

Values a client sends for a computed field follow the same reject-or-ignore setting as other read-only fields (ADR-0014). The metadata endpoint exposes the source.

## Alternatives considered

- **Database computation only.** Requires SQL per provider for everything and gives the client no preview.
- **Application computation only.** Cannot use indexed computed columns or database functions.
- **Leave computed values to application code.** The dictionary would not know which fields are derived, so UIs and validation would treat them as inputs.

## Consequences

- The TypeScript client can preview expression-based values while a user edits; the API value is authoritative.
- Database-computed fields need SQL for every enabled database, and are part of `radd db diff`.
- `persisted` defaults to `true` for application-computed fields (ADR-0028).
