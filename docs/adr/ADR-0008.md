# ADR-0008: Generate migration scripts by diffing the dictionary against a live database

- Status: Accepted
- Date: 2026-10-26
- Deciders: Rommel

## Context

Teams need to move real databases to the schema the dictionary describes. EF migrations compare against a model snapshot, which does not help when an environment's actual state is unknown or has drifted.

## Decision

- `radd db diff --target <name>` compares the dictionary with a live database and writes a timestamped SQL script plus a JSON change report. It never changes a database; applying the script is a separate, explicit step.
- In .NET: build the desired model with `ApplyDataDictionary()`, read the actual schema with EF Core's scaffolding services, compare with EF's migrations model differ, and render SQL with the provider's migrations SQL generator. A stage 2 spike confirms the output is clean; the fallback is a dedicated schema-diff step that still emits SQL through EF's generators.
- Safety rules: only dictionary-owned tables and columns are compared (unknown objects are listed, never dropped); `renamedFrom` turns renames into renames; every operation is tagged safe, needs-data-check or destructive; tightening changes include pre-check queries counting violating rows; destructive changes are excluded unless `--allow-destructive` is passed.
- Normal EF migrations keep working alongside, because the EF model is built from the same dictionary.

## Alternatives considered

- **EF migrations only.** Cannot reconcile drifted or unknown environments.
- **A third-party schema-diff tool.** Another dependency per database, with its own type mapping that may disagree with EF's.
- **Auto-apply.** Unsafe; schema changes must go through the team's deployment process.

## Consequences

- The approach depends on some internal EF services; stage 2 spike C measures the risk.
- `renamedFrom` must be kept until every environment is migrated.
- AI agents can never pass `--allow-destructive`.
