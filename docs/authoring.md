# Authoring a RADD dictionary

A RADD dictionary is a folder of YAML files that defines every entity and field of one system once. The database schema, API validation and front-end behavior are all driven from it. This guide walks through the example in [`examples/acme-orders/dictionary`](../examples/acme-orders/dictionary); the full design is in the [requirements spec](requirements-spec.md).

## Try it

```sh
npm install
npx radd lint examples/acme-orders/dictionary
npx radd build examples/acme-orders/dictionary
```

`radd lint` checks the dictionary ([lint-rules.md](lint-rules.md)); `radd build` writes the canonical JSON to `examples/acme-orders/.radd/dictionary.json` and prints its version hash. Add `--json` to either command for machine-readable output. Set up your editor first ([editor-setup.md](editor-setup.md)) to get autocomplete and inline errors.

## The folder

```
dictionary/
  dictionary.yaml        name, formatVersion, locales, databases, CEL extensions
  types/                 domain types: email.yaml, money.yaml, mobile-number.yaml
  lookups/               static lists: gender.yaml
  entities/              one file per entity: customer.yaml, order-line.yaml, ...
  validators.yaml        named server validators
  calculators.yaml       named server calculators (optional)
  functions.yaml         custom CEL functions (optional)
  i18n/                  en.yaml, fil.yaml (or i18n/en/*.yaml to split a locale)
  AGENTS.md              conventions for AI agents (ignored by radd)
```

File names carry no meaning (each file names what it defines), but lint expects the kebab-case form of the name: `OrderLine` in `order-line.yaml`. Files are YAML 1.2 without anchors, aliases, merge keys or tags, so every file reads on its own.

## dictionary.yaml

```yaml
name: acme-orders
description: Customers and their orders for Acme, the RADD example system.
formatVersion: 1
locales: { default: en, supported: [en, fil] }
databases: [sqlite]
expressions: { extensions: [strings] }
lookups: { defaultTtl: 10m }
```

- `formatVersion` is the RADD file format. The dictionary's own version is the hash `radd build` computes.
- `locales.default` must have every message; other locales fall back to it.
- `databases` lists the providers the dictionary must support; database-computed fields need SQL for each.
- `expressions.extensions` is the declared CEL subset. Functions from other extensions fail lint.

## Domain types

A domain type wraps a logical type with constraints, formats and rules that every field using it inherits.

```yaml
# types/money.yaml
domainType: Money
description: An amount in Philippine pesos, to the centavo.
type: decimal
precision: 12
scale: 2
tags: [financial]
displayFormat: { kind: number, pattern: "#,##0.00" }
editFormat: { kind: number, decimals: 2, grouping: false }
```

A field with `domain: Money` is a decimal(12,2), shown as `1,234,567.50` and edited as `1234567.50`. Fields may override constraints (`min`, `max`, `maxLength`) and formats, but not the base type: `type` and `domain` together are an error.

## Entities and fields

```yaml
# entities/customer.yaml (abridged)
entity: Customer
description: A person or company that places orders.
primaryKey: id
fields:
  id:
    type: guid
    generated: uuid
    description: Surrogate key, generated by the application on create.
  name:
    type: string
    maxLength: 120
    required: true
    description: Full name of the person, or the registered company name.
    tags: [pii]
  email:
    domain: Email
    required: true
    validators: [{ name: uniqueCustomerEmail, severity: error }]
    description: Contact email; must be unique across customers.
  creditLimit:
    domain: Money
    min: 0
    max: 10000000
    description: Maximum unpaid balance allowed before new orders are held.
relationships:
  orders: { kind: oneToMany, entity: Order, foreignKey: customerId }
```

- **Every entity and field needs a `description`.** People and AI agents rely on them.
- **Logical types only:** `string` (needs `maxLength`), `text`, `integer`, `long`, `decimal` (needs `precision` and `scale`), `boolean`, `date`, `time`, `datetime`, `datetimeOffset`, `guid`, `binary`.
- **Names.** Entity names are PascalCase and singular; field names lowerCamelCase. The table defaults to the entity name (`Customer`) and columns to TitleCase (`CreditLimit`); JSON uses camelCase (`creditLimit`). Override with `dbName` or `apiName` to match an existing schema, as `entities/country.yaml` does (`dbName: Countries`, `dbName: IsoCode`).
- **Order matters.** Fields keep their declared order for columns, generated properties and default forms.
- **Defaults** are literals (`default: 0`); computed defaults are `default: { expression: "ctx.now" }`.
- **Generated keys.** `generated: uuid` for guid keys and `generated: identity` for integer or long keys (`entities/province.yaml`). Generated keys are always read-only.
- **Tags** classify fields; `pii` and `financial` values are never logged.

### Lookups

A static list lives in `lookups/`:

```yaml
# lookups/gender.yaml
lookup: gender
description: Gender as stated by the customer.
valueType: string
items:
  - { code: M, label: gender.male }
  - { code: F, label: gender.female }
  - { code: X, label: gender.unspecified, active: false }
```

A field uses it with `lookup: { list: gender }`. Inactive items stay valid for existing data but are not offered for new values.

A reference-table lookup points at another entity, and creates a foreign key:

```yaml
  countryCode:
    type: string
    maxLength: 2
    required: true
    lookup: { entity: Country, value: code, display: name, cache: static }
  provinceId:
    type: integer
    lookup:
      entity: Province
      value: id
      display: name
      cache: ttl
      filter: "row.countryCode == countryCode"
      dependsOn: [countryCode]
```

`provinceId` is a dependent lookup: only provinces of the chosen country are offered and accepted, and the list is refreshed when `countryCode` changes. `cache` is `static` (once per dictionary version), `ttl` (the default, with `lookups.defaultTtl`) or `dynamic`. A plain foreign key that is not a pick list uses `references`, as `OrderLine.orderId` does.

### Rules

```yaml
  vipNotes:
    type: text
    rules:
      - when: "creditLimit > 1000000.0"
        required: true
        severity: warning
        message: customer.vipNotes.recommended
```

A conditional rule switches `required`, `readOnly` or `visible` while its CEL `when` is true. An expression rule is `{ expression: "endDate >= startDate", message: ... }` and must name a message. Severities: `error` rejects the save; `warning` rejects it until the client acknowledges the code; `info` only informs. A rule's code defaults to its message key.

### Named validators and computed fields

Validators that need the database or other systems are declared once and used by name:

```yaml
# validators.yaml
validators:
  uniqueCustomerEmail:
    scope: field
    description: Rejects an email already used by another customer, ignoring case.
```

Computed fields declare their source and are always read-only:

```yaml
  lineTotal:
    type: decimal
    precision: 14
    scale: 2
    computed: { source: application, expression: "dec.mul(quantity, unitPrice)", persisted: true }
```

Decimal arithmetic uses the `dec.*` functions so every runtime gets the exact result.

## Display and edit metadata

Formats use ICU patterns and are presentation only: the API stores and returns raw values.

```yaml
# types/mobile-number.yaml
domainType: MobileNumber
type: string
maxLength: 11
pattern: "^09[0-9]{9}$"
displayFormat: { kind: text, mask: "0000-000-0000" }
editFormat: { kind: mask, pattern: "0000-000-0000", storeLiterals: false }
```

The number is stored as `09171234567`, shown and typed as `0917-123-4567`, and validated with an RE2 pattern. `entities/order.yaml` shows a date: `displayFormat: { kind: date, style: medium }` and `editFormat: { kind: date, pattern: "yyyy-MM-dd" }`.

## Text and translations

All user-facing text lives in `i18n/<locale>.yaml` as a flat map of keys to ICU MessageFormat text. Keys are derived from the path:

| Key | Required | Example |
| --- | --- | --- |
| `<entity>.displayLabel` | yes | `customer.displayLabel: Customer` |
| `<entity>.pluralLabel`, `<entity>.displayHint` | no | `customer.pluralLabel: Customers` |
| `<entity>.<field>.displayLabel` | yes | `customer.creditLimit.displayLabel: Credit limit` |
| `<entity>.<field>.shortLabel`, `.displayHint`, `.placeholder` | no | `customer.mobileNumber.placeholder: 0917-123-4567` |
| `<entity>.<field>.<constraint>` | no | `customer.mobileNumber.pattern: Enter an 11-digit mobile number starting with 09.` |
| `<domainType>.<constraint>` | no | `money.min: Amounts cannot be negative.` |
| explicit `message` keys | yes | `customer.vipNotes.recommended: ...` |

Constraint messages fall back from the field key to the domain-type key to the framework message (`radd.required`, `radd.maxLength`, ...). RADD ships the framework messages in English; other locales should translate them (see `i18n/fil.yaml`). Messages use ICU placeholders: `{label}` is the field's display label.

Display hints may contain a little HTML (`b`, `strong`, `i`, `em`, `br`, `p`, `ul`, `ol`, `li`, `code`, and `a` with an `https` link):

```yaml
customer.creditLimit.displayHint: "Maximum unpaid balance, in pesos. <b>Requires approval</b> above 1,000,000."
```

## The canonical JSON

`radd build` merges the folder into one document: domain types expanded into fields, defaults written out (`required: false`, `readOnly: never`, `dbName`, `apiName`, index names), message keys resolved, and keys sorted. Its `version` is `sha256:` plus the SHA-256 of the RFC 8785 canonical form, so it changes when any value changes and not when you reformat, reorder keys, rename files or split a locale. The example's output is checked in as [`conformance/build/acme-orders/expected.json`](../conformance/build/acme-orders/expected.json), so any change shows up in review.

## Changing a dictionary safely

- Run `npx radd lint` before every commit; CI runs it too.
- To rename an entity or field, change the name and add `renamedFrom: oldName`, so migrations rename instead of dropping and adding. Remove `renamedFrom` once every database is migrated.
- Keep every supported locale in step; lint warns about missing translations.
